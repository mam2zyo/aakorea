# DOMAIN_MODEL

## 이 문서의 역할

이 문서는 AAKorea Main 웹앱의 현재 MVP에서 **어떤 개체를 핵심 도메인으로 채택하는지**, 그리고 **각 개체를 어떤 의미와 경계로 이해하는지** 정의한다.

이 문서가 답하는 질문:

- 현재 MVP에서 어떤 개체를 도메인으로 본다?
- 각 개체는 어떤 역할을 갖는가?
- 개체 간 관계는 어떻게 이해하는가?
- 어떤 개념은 아직 별도 개체로 만들지 않는가?

이 문서에 포함하지 않는 내용:

- 제품 범위의 상세 판단
- 사용자별 목표와 행동 흐름
- 엔티티별 최소 필드 목록
- API 요청/응답 계약
- 구현 단계별 작업 순서
- 콘텐츠 모델의 세부 분류 기준

---

## 현재 핵심 도메인 개체

현재 MVP에서 핵심 도메인으로 채택하는 개체는 다음과 같다.

- `District`
- `Group`
- `GroupContact`
- `Meeting`
- `ContentPage`
- `Notice`

이 개체들은 현재 MVP의 공개 탐색 흐름과 최소 운영 흐름을 성립시키는 데 직접 필요하다.

---

## 개체별 정의

### 1. District

`District`는 운영 조직 관점의 상위 구분 단위다.

이 개체는 공개 탐색의 직접 단위라기보다,  
운영자가 그룹과 관련 정보를 관리할 때 기준이 되는 조직 단위다.

현재 MVP에서 `District`는 다음 의미를 가진다.

- 운영상 그룹을 소속시키는 기준
- 그룹 관리의 상위 단위
- 조직 구조를 최소한으로 표현하는 단위

현재는 `District`를 복잡한 트리 구조나 다단계 조직 모델로 확장하지 않는다.

---

### 2. Group

`Group`은 실제 운영과 연락의 중심이 되는 기본 조직 단위다.

현재 MVP에서 `Group`은 다음 의미를 가진다.

- 운영자가 관리하는 실질 조직 단위
- 연락처와 모임이 연결되는 중심 단위
- 공개 정보와 운영 정보가 만나는 핵심 단위

`Group`은 `District`에 소속된다.  
또한 하나 이상의 `GroupContact` 및 `Meeting`과 연결될 수 있다.

현재 MVP에서 `Group`은 독립적인 지역 탐색 단위로 보지 않는다.  
사용자가 직접 찾는 것은 기본적으로 `Meeting`이며, `Group`은 그 배경 조직으로 이해한다.

---

### 3. GroupContact

`GroupContact`는 `Group`과 연결된 연락 지점을 표현하는 개체다.

현재 MVP에서 이 개체는 특히 중요하다.  
이유는 공개 사용자의 핵심 목표 중 하나가 **실제로 연락 가능한 번호에 도달하는 것**이기 때문이다.

현재 MVP에서 `GroupContact`는 다음 의미를 가진다.

- 공개 연락을 가능하게 하는 연결 지점
- 그룹에 속한 전화 기반 연락처
- 공개 화면에서 확인 가능한 핵심 정보의 일부

현재는 `GroupContact`를 범용 연락 수단 모델로 일반화하지 않는다.  
즉, 이메일, 메신저, 다중 채널, 복잡한 연락 정책 등으로 확장하지 않고,  
**그룹에 연결된 최소 연락처 개체**로 본다.

---

### 4. Meeting

`Meeting`은 공개 사용자가 실제로 탐색하는 핵심 개체다.

현재 MVP에서 `Meeting`은 다음 의미를 가진다.

- 사용자가 지역 기준으로 찾는 대상
- 실제 참여 가능성을 판단하는 공개 정보 단위
- `Group`과 연결되지만, 공개 탐색에서는 더 직접적인 단위

즉, 현재 MVP의 공개 핵심 흐름은 `Group` 검색이 아니라 **`Meeting` 검색**이다.

`Meeting`은 `Group`에 속한다.  
사용자는 `Meeting`을 통해 기본 정보와 연락 가능한 지점에 접근한다.

`Meeting`은 `MeetingLocation` 값을 포함한다.  
현재 MVP에서 `MeetingLocation`은 `Meeting`에 종속된 value object로 보며,  
별도 식별자나 독립 관리 흐름을 갖지 않는다.

`Meeting`은 `MeetingType` 값을 가진다.  
현재 MVP에서 `MeetingType`은 모임의 공개/비공개 성격을 표현하는 enum이며,  
복잡한 예외 일정까지 세밀하게 모델링하지 않는 현재 단계의 제약을 함께 반영한다.

현재 MVP에서는 `Meeting`을 매우 복잡한 일정 모델로 다루지 않는다.  
반복 규칙, 예외 일정, 특별 이벤트 분기 같은 확장은 도입하지 않는다.

---

### MeetingType (enum)

`MeetingType`은 `Meeting`의 공개 가능성 성격을 표현하는 enum 값이다.

현재 MVP에서 허용하는 값은 다음과 같다.

- `OPEN`
- `CLOSED`
- `NOTFIXED`

각 값의 의미는 아래와 같다.

- `OPEN`: 일관되게 공개 모임으로 이해할 수 있는 경우
- `CLOSED`: 일관되게 비공개 모임으로 이해할 수 있는 경우
- `NOTFIXED`: 단일한 `OPEN` 또는 `CLOSED`로 표현하기 어려운 경우

`NOTFIXED`는 현재 MVP가 복잡한 예외 일정 모델을 갖지 않기 때문에 필요한 값이다.  
예를 들어 목요일 모임이 기본적으로는 비공개지만 마지막 주만 공개 모임인 경우,  
현재 단계에서는 이를 상세 규칙으로 분해하지 않고 `NOTFIXED`로 표현한다.

---

### MeetingLocation (value object)

`MeetingLocation`은 `Meeting`에 포함되는 위치 정보 값 객체다.

현재 MVP에서 `MeetingLocation`은 다음 의미를 가진다.

- 사용자가 모임 장소를 식별하고 이동하는 데 필요한 최소 위치 정보
- `Meeting`과 함께 입력·수정·조회되는 내부 구성 요소
- 별도 식별자 없이 공개 정보 일부를 구성하는 값

현재는 `MeetingLocation`을 독립 엔티티나 범용 `Place`로 일반화하지 않는다.  
즉, 장소 재사용, 독립 장소 카탈로그, 지도 중심 확장은 이후 단계 검토 대상으로 둔다.

---

### 5. ContentPage

`ContentPage`는 비교적 안정적인 정적/안내성 콘텐츠를 표현하는 개체다.

현재 MVP에서 `ContentPage`는 다음 의미를 가진다.

- 소개, 안내, 설명과 같은 정적 콘텐츠 단위
- 방문자가 서비스 목적과 기본 정보를 이해하는 데 필요한 정보 단위
- 운영자가 직접 관리하는 공개 정보 단위

이 개체는 공지성 정보나 시간 민감한 게시물을 위한 모델이 아니다.  
그 역할은 `Notice`와 구분한다.

`ContentPage`를 범용 CMS 구조로 확장하는 것은 현재 MVP 목표가 아니다.

---

### 6. Notice

`Notice`는 공지성, 시의성, 업데이트성 정보를 표현하는 개체다.

현재 MVP에서 `Notice`는 다음 의미를 가진다.

- 공개 사용자에게 보여줄 공지 단위
- 운영자가 등록·수정하는 최신 안내성 정보
- 정적 안내와 구분되는 시의성 정보 단위

`Notice`는 `ContentPage`와 목적이 다르다.  
`ContentPage`가 비교적 안정적인 설명 콘텐츠라면, `Notice`는 변동 가능성이 있는 공지 콘텐츠다.

현재 MVP에서는 `Notice`를 범용 게시판 구조로 확장하지 않는다.

---

## 개체 간 관계

현재 MVP의 핵심 관계는 아래처럼 이해한다.

### District → Group

- 하나의 `District`는 여러 `Group`을 가질 수 있다
- `District`는 운영 조직 기준이며, `Group`은 실질 운영 단위다

### Group → GroupContact

- 하나의 `Group`은 하나 이상의 `GroupContact`를 가질 수 있다
- `GroupContact`는 그룹과 연결된 실제 연락 지점이다

### Group → Meeting

- 하나의 `Group`은 하나 이상의 `Meeting`을 가질 수 있다
- `Meeting`은 공개 탐색의 직접 대상이다

### Meeting → MeetingLocation (value object)

- 하나의 `Meeting`은 하나의 `MeetingLocation` 값을 포함한다

### ContentPage, Notice

- `ContentPage`와 `Notice`는 조직/모임 구조와 별개로 관리되는 공개 콘텐츠 개체다
- 두 개체는 모두 공개 정보에 속하지만, 목적과 성격이 다르다

---

## 현재 모델링의 핵심 판단

현재 MVP에서는 아래 판단을 유지한다.

### 1. 공개 탐색의 중심은 Group이 아니라 Meeting이다

사용자가 찾는 것은 “어떤 그룹이 존재하는가”보다  
“내가 참여 가능한 모임이 어디 있는가”에 가깝다.

따라서 현재 공개 흐름의 중심 개체는 `Meeting`이다.

---

### 2. 운영 조직의 중심은 District와 Group이다

운영 측면에서는 조직 관리 기준이 필요하므로 `District`와 `Group`을 둔다.

다만 현재는 이를 복잡한 조직도나 계층 구조로 확장하지 않는다.

---

### 3. 연락 가능성은 별도 개체로 분리한다

연락 정보는 단순한 부가 속성이 아니라,  
현재 MVP의 핵심 가치 중 하나인 “실제 연결 가능성”을 담당한다.

따라서 `GroupContact`를 별도 개체로 둔다.

---

### 4. 장소 정보는 `Meeting` 내부의 값 객체로 둔다

현재 MVP에서 장소 정보는 독립 식별자와 수명주기를 가진 개체보다,  
`Meeting`과 함께 관리되는 값이 더 적합하다.

따라서 `MeetingLocation`을 별도 핵심 개체가 아니라 `Meeting` 내부 value object로 둔다.

---

### 5. 안내성 콘텐츠와 공지성 콘텐츠를 구분한다

공개 사이트의 정보는 모두 같은 성격이 아니다.

- 비교적 안정적인 설명/안내
- 시간에 따라 바뀌는 공지/업데이트

이 둘은 운영 방식과 노출 방식이 다르므로 `ContentPage`와 `Notice`를 분리한다.

---

## 현재 별도 핵심 개체로 채택하지 않는 것

현재 MVP에서는 아래 개념을 별도 핵심 도메인 개체로 채택하지 않는다.

### 1. Province

`Province`는 현재 MVP에서 매우 중요한 값이지만,  
이 문서에서는 이를 독립 핵심 도메인 개체로 보지 않는다.

현재 단계에서 `Province`는 **공개 탐색 기준으로 사용하는 지역 값**으로 이해한다.  
즉, 사용자는 지역 기준으로 `Meeting`을 찾지만, 현재 모델의 중심 개체는 여전히 `Meeting`이다.

`Province`의 필드/표현 방식은 `MVP_FIELDS.md`에서 다룬다.

---

### 2. 별도 장소 엔티티 / Place

현재 MVP에서는 장소 정보를 별도 핵심 개체로 채택하지 않는다.

현재 단계에서 장소 정보는 `Meeting`에 포함되는 `MeetingLocation` value object로 이해한다.  
즉, 별도 장소 엔티티나 범용 `Place` 같은 독립 엔티티는 현재 모델에 포함하지 않는다.

장소 재사용, 독립 장소 카탈로그, 지도 중심 일반화는 이후 단계에서 검토할 수 있다.

---

### 3. Board / Post

범용 게시판 구조는 현재 MVP에서 채택하지 않는다.

현재 공개 정보는 `ContentPage`와 `Notice`로 충분히 처리한다.  
게시판형 확장은 이후 단계 검토 대상으로 둔다.

---

### 3. Committee

위원회성 조직 모델은 현재 MVP 핵심 흐름에 직접 필요하지 않다.  
따라서 별도 핵심 개체로 채택하지 않는다.

---

### 4. Conference / Event

행사/컨퍼런스 중심 모델은 현재 모임 탐색 MVP의 직접 범위가 아니다.  
따라서 현재는 별도 핵심 개체로 두지 않는다.

---

### 5. MeetingAnnouncement

모임별 개별 공지 모델은 현재 별도 핵심 개체로 두지 않는다.

현재 단계에서는 `Notice`와 `ContentPage`의 범위 안에서 충분한지 먼저 본다.  
필요 시 이후에 분리한다.

---

### 6. 범용 ContactPoint

현재는 `GroupContact`가 핵심 요구를 충족한다.  
조직 전체에 걸친 범용 연락 포인트 모델로 일반화하지 않는다.

---

## 모델 단순화 원칙

현재 MVP의 도메인 모델은 아래 원칙을 따른다.

### 1. 핵심 흐름을 직접 지지하는 개체만 채택한다

도메인 개체는 “있으면 좋다”가 아니라,  
공개 탐색과 최소 운영 흐름에 직접 기여할 때만 채택한다.

### 2. 조직 구조를 과도하게 일반화하지 않는다

현재는 최소한의 운영 조직 구조만 표현한다.  
복잡한 계층화, 역할 분기, 조직 유형 다양화는 보류한다.

### 3. 콘텐츠 구조를 과도하게 CMS화하지 않는다

현재는 `ContentPage`와 `Notice` 수준의 구분만 둔다.  
범용 게시판, 미디어 중심 콘텐츠 모델, 복잡한 문서 체계는 도입하지 않는다.

### 4. 일정 구조를 과도하게 이벤트 시스템화하지 않는다

현재의 `Meeting`은 공개 탐색을 위한 최소 단위다.  
복잡한 반복 일정, 세션 구조, 행사 운영 모델은 현재 다루지 않는다.

---

## 현재 도메인 모델 요약

현재 MVP의 도메인 모델은 다음처럼 요약할 수 있다.

- 운영 조직 기준은 `District`
- 실질 운영 단위는 `Group`
- 연락 가능 지점은 `GroupContact`
- 공개 탐색 중심은 `Meeting`
- 모임 위치 정보는 `MeetingLocation` value object
- 정적 안내 콘텐츠는 `ContentPage`
- 시의성 공지는 `Notice`

이 구조는 **지역 기준 모임 탐색과 최소 운영 관리**라는 현재 MVP 목적을 만족시키기 위한 최소 모델이다.
