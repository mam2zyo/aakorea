# IMPLEMENTATION_PLAN

## 이 문서의 역할

이 문서는 AAKorea Main 웹앱의 현재 MVP를 **어떤 순서로 구현할지**, 그리고 **각 단계가 언제 완료된 것으로 볼 수 있는지**를 정의한다.

이 문서가 답하는 질문:

- 무엇부터 구현하는가?
- 각 단계의 목표는 무엇인가?
- 각 단계의 완료 기준은 무엇인가?
- 단계 간 선행 관계는 무엇인가?

이 문서에 포함하지 않는 내용:

- 제품 범위의 상세 판단
- 사용자별 목표와 행동 흐름
- 도메인 개체의 의미와 관계 설명
- 엔티티별 최소 필드 목록
- API 요청/응답 계약

---

## 구현 우선순위 원칙

현재 MVP 구현은 아래 원칙을 따른다.

### 1. 공개 핵심 흐름을 가장 먼저 성립시킨다

현재 MVP의 핵심은 **지역 기준 모임 탐색과 연락 연결**이다.  
따라서 공개 사용자가 실제로 모임을 찾고 연락처를 확인할 수 있는 흐름을 우선한다.

### 2. 운영 기능은 공개 흐름을 유지하는 최소 범위만 먼저 구현한다

운영 기능은 필요하지만, 초기 단계에서는 공개 흐름을 지탱하는 최소 관리 기능만 구현한다.

### 3. 모델 확장보다 수직 흐름 완성을 우선한다

도메인을 넓히기보다,  
한 개의 흐름이 처음부터 끝까지 작동하도록 만드는 것을 우선한다.

### 4. 각 단계는 독립적인 검증 가능 상태를 만들어야 한다

각 단계는 “구현했다”가 아니라,  
실제로 동작 여부를 확인할 수 있는 상태로 끝나야 한다.

---

## 전체 단계 개요

현재 MVP는 아래 순서로 구현한다.

1. 프로젝트 기반과 공통 규약 정리
2. 운영 인증 흐름 구현
3. District / Group / GroupContact 관리 구현
4. Meeting 관리 및 공개 조회 구현
5. ContentPage / Notice 관리 및 공개 조회 구현
6. 공개 화면 핵심 흐름 연결
7. 운영 화면 최소 흐름 정리
8. 통합 점검 및 MVP 마감

이 순서는 **운영 입력 → 공개 노출 → 사용자 흐름 완성**의 방향을 따른다.

## 1단계. 프로젝트 기반과 공통 규약 정리

### 목표

백엔드/프론트엔드에서 이후 구현의 공통 기준이 되는 최소 기반을 준비한다.

### 구현 대상

- 프로젝트 기본 실행 구조
- 공통 예외 처리 방식
- 공통 응답 형식
- 인증/비인증 API 구분 구조
- 기본 라우팅 또는 화면 골격
- Province / DayOfWeek 등 공통 선택값 관리 방식

### 선행 조건

- 없음

### 완료 기준

- 백엔드와 프론트엔드가 기본 실행 가능하다
- `/api/public/*`, `/api/admin/*`, `/api/auth/*` 구조를 사용할 수 있다
- 공통 성공/실패 응답 형식이 정리되어 있다
- 최소한의 개발용 환경에서 API 호출과 화면 연결이 가능하다

### 참고 문서

- API 규약: `api/COMMON.md`
- 최소 필드: `MVP_FIELDS.md`

## 2단계. 운영 인증 흐름 구현

### 목표

운영자가 로그인하여 관리 기능에 접근할 수 있는 최소 인증 흐름을 만든다.

### 구현 대상

- 운영자 로그인
- 로그아웃
- 현재 세션 확인
- 인증 필요한 경로 보호
- 운영 화면 진입 제어

### 선행 조건

- 1단계 완료

### 완료 기준

- 운영자가 로그인할 수 있다
- 미인증 상태에서는 운영 API 접근이 차단된다
- 운영 화면 진입 시 인증 상태를 확인할 수 있다
- 로그아웃 후 운영 API 접근이 불가능하다

### 범위 제한

- 현재는 복잡한 역할 분기나 권한 매트릭스를 구현하지 않는다
- 최소 운영자 인증만 구현한다

### 참고 문서

- 범위 기준: `PRODUCT_SCOPE.md`
- API 계약: `api/AUTH.md`

## 3단계. District / Group / GroupContact 관리 구현

### 목표

운영자가 공개 흐름의 기반이 되는 조직과 연락 정보를 관리할 수 있게 한다.

### 구현 대상

- District 목록/생성/수정
- Group 목록/생성/수정
- GroupContact 목록/생성/수정
- 운영 화면에서 각 데이터의 기본 관리 UI

### 선행 조건

- 2단계 완료

### 완료 기준

- 운영자가 District를 생성하고 수정할 수 있다
- 운영자가 Group을 District에 연결하여 생성하고 수정할 수 있다
- 운영자가 GroupContact를 Group에 연결하여 생성하고 수정할 수 있다
- 비활성 상태를 포함한 최소 상태 관리가 가능하다
- 이후 Meeting과 공개 조회에 필요한 참조 기반이 준비된다

### 검증 포인트

- Group이 District와 올바르게 연결되는가
- GroupContact가 Group에 올바르게 연결되는가
- 연락처 관리가 실제 공개 흐름에 활용 가능한 수준인가

### 참고 문서

- 도메인 경계: `DOMAIN_MODEL.md`
- 최소 필드: `MVP_FIELDS.md`
- API 계약: `api/ADMIN_ORG.md`

## 4단계. Meeting 관리 및 공개 조회 구현

### 목표

현재 MVP의 핵심인 **지역 기준 모임 탐색 흐름**을 성립시킨다.

### 구현 대상

- 운영자의 Meeting 목록/생성/수정
- 공개용 Meeting 목록 조회
- 공개용 Meeting 상세 조회
- Province 기준 조회
- 필요 시 DayOfWeek 기준 보조 필터

### 선행 조건

- 3단계 완료

### 완료 기준

- 운영자가 Group에 연결된 Meeting을 생성하고 수정할 수 있다
- 공개 사용자가 Province 기준으로 Meeting 목록을 조회할 수 있다
- 공개 사용자가 Meeting 상세를 조회할 수 있다
- Meeting 상세에서 연락 가능한 전화번호를 확인할 수 있다
- 비활성 Meeting은 공개 조회에서 제외된다

### 검증 포인트

- 현재 공개 탐색의 중심이 `Meeting`으로 동작하는가
- Province 기준 탐색이 실제 사용 흐름을 만족하는가
- GroupContact가 공개 상세 화면과 안정적으로 연결되는가

### 이 단계의 의미

이 단계가 완료되면, 현재 MVP의 가장 중요한 사용자 가치가 처음으로 동작한다.

### 참고 문서

- 공개 핵심 흐름: `ACTORS_AND_USE_CASES.md`
- 도메인 경계: `DOMAIN_MODEL.md`
- 최소 필드: `MVP_FIELDS.md`
- API 계약: `api/PUBLIC_MEETINGS.md`, `api/ADMIN_MEETINGS.md`

## 5단계. ContentPage / Notice 관리 및 공개 조회 구현

### 목표

공개 사이트의 기본 안내와 공지 흐름을 구현한다.

### 구현 대상

- ContentPage 목록/생성/수정
- Notice 목록/생성/수정
- 공개용 ContentPage 조회
- 공개용 Notice 목록/상세 조회

### 선행 조건

- 2단계 완료
- 1단계 완료

### 완료 기준

- 운영자가 안내성 페이지를 생성하고 수정할 수 있다
- 운영자가 공지를 생성하고 수정할 수 있다
- 공개 사용자가 key 기반으로 ContentPage를 조회할 수 있다
- 공개 사용자가 Notice 목록과 상세를 조회할 수 있다
- 게시되지 않은 데이터는 공개 화면에 노출되지 않는다

### 검증 포인트

- `ContentPage`와 `Notice`의 역할 차이가 운영 화면과 공개 화면에서 유지되는가
- 안내 콘텐츠와 공지 콘텐츠가 혼동되지 않는가

### 참고 문서

- 콘텐츠 구분 기준: `CONTENT_MODEL.md`
- 최소 필드: `MVP_FIELDS.md`
- API 계약: `api/PUBLIC_CONTENT.md`, `api/ADMIN_CONTENT.md`

## 6단계. 공개 화면 핵심 흐름 연결

### 목표

방문자가 사이트 안에서 자연스럽게 핵심 행동을 수행할 수 있도록 공개 화면을 연결한다.

### 구현 대상

- 홈 또는 진입 화면
- 기본 소개/안내 진입
- 공지 진입
- 지역 기준 모임 탐색 화면
- 모임 상세 화면
- 연락처 확인 흐름

### 선행 조건

- 4단계 완료
- 5단계 완료

### 완료 기준

- 방문자가 사이트 진입 후 기본 목적을 이해할 수 있다
- 방문자가 안내 페이지에 접근할 수 있다
- 방문자가 공지를 확인할 수 있다
- 방문자가 지역 기준으로 모임을 찾을 수 있다
- 방문자가 모임 상세에서 연락 가능한 번호를 확인할 수 있다

### 검증 포인트

- “처음 방문 → 안내 확인 → 지역 선택 → 모임 조회 → 연락처 확인” 흐름이 자연스럽게 이어지는가
- 핵심 공개 기능이 별도 설명 없이도 이해 가능한가

### 참고 문서

- 사용자 흐름: `ACTORS_AND_USE_CASES.md`
- 범위 기준: `PRODUCT_SCOPE.md`

## 7단계. 운영 화면 최소 흐름 정리

### 목표

운영자가 핵심 데이터를 큰 혼란 없이 관리할 수 있는 최소 운영 흐름을 정리한다.

### 구현 대상

- 운영 홈 또는 기본 메뉴
- District / Group / GroupContact 관리 화면
- Meeting 관리 화면
- ContentPage / Notice 관리 화면
- 로그인 직후 사전 정렬된 목록 중심 운영 인덱스
- 좁은 화면에서 목록 → 상세 진입이 가능한 반응형 운영 레이아웃
- 공개 결과 확인 동선

### 선행 조건

- 3단계 완료
- 4단계 완료
- 5단계 완료

### 완료 기준

- 운영자가 로그인 후 필요한 관리 메뉴에 접근할 수 있다
- 운영자가 로그인 직후 기본 정렬이 적용된 관리 목록을 바로 확인할 수 있다
- 운영자가 핵심 데이터를 생성·수정할 수 있다
- 운영자가 입력 결과를 공개 화면에서 확인할 수 있다
- 초기 운영에 필요한 최소 관리 흐름이 끊기지 않는다
- 이후 온라인 모임 관리, 제12단계 운동 관리 메뉴를 무리 없이 추가할 수 있는 운영 메뉴 구조가 마련된다

### 검증 포인트

- 운영자가 어떤 정보를 어디서 관리해야 하는지 혼동하지 않는가
- 공개/운영 간 연결 상태를 쉽게 확인할 수 있는가
- 좁은 화면에서도 목록 가독성과 편집 진입 흐름이 유지되는가

### 범위 제한

- 이 단계에서도 고급 대시보드, 권한 세분화, 대량 편집은 우선하지 않는다
- 초기 목록은 필요한 최소 컬럼만 노출하며, 연락처/회원수/등록일/상태 같은 보조 컬럼은 기본 목록에서 제외한다
- 페이징은 데이터 규모가 실제로 커질 때 도입하되, 기본 정렬과 향후 확장 가능한 목록 구조를 먼저 정리한다

### 참고 문서

- 사용자 행동: `ACTORS_AND_USE_CASES.md`
- API 계약: `api/README.md`

## 8단계. 통합 점검 및 MVP 마감

### 목표

현재 MVP가 실제 사용 가능한 최소 수준에 도달했는지 통합 관점에서 점검한다.

### 구현 대상

- 핵심 시나리오 점검
- 공개/운영 연결 검증
- 기본 오류 처리 확인
- 비활성/비게시 상태 확인
- 최소 문서 및 실행 방법 정리

### 선행 조건

- 6단계 완료
- 7단계 완료

### 완료 기준

- 방문자 핵심 흐름이 처음부터 끝까지 동작한다
- 운영자 핵심 흐름이 처음부터 끝까지 동작한다
- 공개 API와 운영 API가 최소 계약을 만족한다
- 핵심 데이터 상태값이 공개 노출에 반영된다
- 프로젝트를 실행하고 검증하는 최소 방법이 문서화되어 있다

### 최종 검증 시나리오

- 운영자가 로그인한다
- District / Group / GroupContact / Meeting을 입력한다
- 공개 사용자가 Province 기준으로 Meeting을 찾는다
- 공개 사용자가 상세에서 연락처를 확인한다
- 운영자가 ContentPage / Notice를 입력한다
- 공개 사용자가 안내와 공지를 확인한다

## 단계 간 선행 관계 요약

### 강한 선행 관계

- 1단계 → 2단계
- 2단계 → 3단계
- 3단계 → 4단계
- 4단계 + 5단계 → 6단계
- 3단계 + 4단계 + 5단계 → 7단계
- 6단계 + 7단계 → 8단계

### 상대적으로 독립적인 축

- 5단계는 4단계와 병행 가능성이 있다
- 다만 공개 화면 연결 전에는 둘 다 완료되는 편이 좋다

## 현재 MVP의 최소 완료 기준

현재 MVP는 아래 조건을 만족하면 1차 완료로 본다.

### 공개 측면

- 안내 페이지 조회 가능
- 공지 목록/상세 조회 가능
- Province 기준 모임 조회 가능
- 모임 상세에서 연락 가능한 번호 확인 가능

### 운영 측면

- 운영자 로그인 가능
- District / Group / GroupContact / Meeting 관리 가능
- ContentPage / Notice 관리 가능

### 전체 연결 측면

- 운영 입력이 공개 화면에 반영된다
- 비활성/비게시 데이터가 공개에 잘못 노출되지 않는다
- 핵심 시나리오가 수동 검증 가능하다

## 현재 보류하는 구현 항목

아래 항목은 현재 구현 계획의 직접 범위에 포함하지 않는다.

- 일반 사용자 계정 기능
