# Git Workflow 및 버전 관리 전략

*   **역할**: AAKorea Main 프로젝트의 브랜치 관리 전략 및 커밋 프로세스를 정의한다.
*   **포함하지 않는 내용**: 개별 Git 명령어의 상세 설명 (Git 기본 교육 제외).

---

## 1. 브랜치 전략 (Branching Strategy)

본 프로젝트는 `develop` 브랜치를 중심으로 하는 변형된 **GitHub Flow** 전략을 따릅니다.

### 1.1 주요 브랜치 (Main Branches)

| 브랜치명 | 역할 | 머지 주기 | 비고 |
| :--- | :--- | :--- | :--- |
| `main` | **배포 브랜치 (Stable)** | 서비스 릴리즈 시에만 | 항상 빌드 및 배포 가능한 상태 유지 |
| `develop` | **통합 브랜치 (Integration)** | 수시 (일상 개발) | 기본 개발 브랜치. 모든 피처의 베이스 |

### 1.2 보조 브랜치 (Supporting Branches)

| 브랜치명 | 생성 대상 | 머지 대상 | 역할 |
| :--- | :--- | :--- | :--- |
| `feat/**` | `develop` | `develop` | 새로운 기능 개발 |
| `fix/**` | `develop` | `develop` | 버그 수정 또는 UI 개선 |
| `refactor/**` | `develop` | `develop` | 코드 리팩토링 및 성능 개선 |

---

## 2. 개발 프로세스 (Development Process)

### 2.1 소규모 작업 및 단순 수정
*   오타 수정, 간단한 스타일 변경, 영향도가 매우 낮은 버그 수정의 경우 **`develop` 브랜치에 직접 커밋**이 허용됩니다.
*   단, 커밋 직전에 반드시 로컬 `develop`을 최신 상태로 유지하고 테스트를 거쳐야 합니다.

### 2.2 기능 개발 및 복잡한 작업
1.  `develop` 브랜치에서 새로운 작업 브랜치(`feat/name`)를 생성합니다.
2.  해당 브랜치에서 기능을 구현하고 테스트를 완료합니다.
3.  필요한 경우 `develop` 브랜치의 최신 내용을 `merge`하여 충돌을 미리 해결합니다.
4.  작업이 완료되면 `develop`으로 합병합니다.

## 3. Pull Request (PR) 및 머지 규칙

코드 품질 유지와 가독성을 위해 아래의 경우 반드시 PR을 생성합니다.

### 3.1 PR 생성이 필수가 되는 경우
*   **복잡한 비즈니스 로직**의 변경이 포함된 경우
*   **데이터베이스 스키마**나 주요 API 계약이 변경되는 경우
*   협업자가 해당 변경 사항을 반드시 **검토(Code Review)**해야 할 필요가 있는 경우
*   여러 브랜치를 하나로 모으는 대규모 배포 준비인 경우

### 3.2 `main` 브랜치 머지 규칙 (강제)
*   **`main` 브랜치로의 모든 머지는 반드시 GitHub PR을 통해서만 진행합니다.**
*   `main`에 직접 `push` 하는 행위는 금지됩니다. (배포 기록 및 안정성 확보를 위함)

---

## 4. 커밋 메시지 가이드 (Commit Message)

프로젝트 히스토리를 명확히 하기 위해 아래와 같은 접두어를 권장합니다.

*   `feat`: 신규 기능 추가
*   `fix`: 버그 수정
*   `perf`: 성능 개선
*   `refactor`: 기능 변경 없는 코드 리팩토링
*   `style`: 코드 포맷팅, 스타일 수정 (로직 변경 없음)
*   `docs`: 문서 수정 (README, Wiki 등)
