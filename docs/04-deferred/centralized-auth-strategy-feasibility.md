# 중앙 집중형 인증(Auth Server) 및 멀티 레포지토리 전략 검토

이 문서는 서비스를 서브도메인별로 완전히 독립된 저장소로 분리하고, 인증 로직을 중앙화된 서버(`auth.aakorea.org`)에서 관리하는 아키텍처의 구현 가능성과 세부 전략을 분석합니다.

---

## 1. 구현 가능성 (Feasibility Study)

결론부터 말씀드리면, **구현 가능성은 매우 높으며** 규모가 커지는 서비스 환경에서 흔히 채택되는 표준 아키텍처입니다.

- **스프링 부트 지원**: `Spring Authorization Server`를 통해 OAuth2, OpenID Connect(OIDC) 규격을 따르는 자체 인증 서버를 구축할 수 있는 성숙한 도구가 존재합니다.
- **인프라 호환성**: Vercel(프론트)과 AWS(백엔드)가 이미 분리되어 있으므로, 새로운 백엔드 서비스(Auth)를 추가하고 별도의 도메인을 할당하는 데 기술적 제약이 없습니다.

---

## 2. 핵심 기술 전략

### 2.1 인증 서버 (Identity Provider, IdP)
`auth.aakorea.org`는 모든 서비스의 **"단일 인증 원천"**이 됩니다.
- **역할**: 로그인 UI 제공, 사용자 계정 관리, 액세스 토큰(JWT) 및 리프레시 토큰 발행.
- **데이터베이스**: 모든 서비스가 공유하는 `User` 및 `Permission` 테이블이 있는 중앙 DB를 바라봅니다.

### 2.2 리소스 서버 (Resource Servers)
`store.`, `heart.` 등의 개별 백엔드 서비스는 스스로 로그인을 처리하지 않고, 들어오는 토큰이 `auth.` 서버에서 발행된 것인지 검증만 수행합니다.
- **방식**: Spring Security의 OAuth2 Resource Server 모듈을 사용하여 구현이 간단합니다.

### 2.3 프론트엔드 SSO (Single Sign-On)
사용자가 한 곳에서 로그인하면 모든 서브도메인에서 인증이 유지되어야 합니다.
- **방법 1 (쿠키 공유)**: 모든 서브도메인이 `.aakorea.org`라는 공통 부모 도메인의 세션 쿠키를 공유합니다. (가장 구현이 쉬움)
- **방법 2 (OAuth2 Flow)**: 각 앱이 인증이 필요할 때 `auth.aakorea.org`로 리다이렉트되어 인증을 받고 돌아옵니다. (가장 표준적이고 보안성이 높음)

---

## 3. 멀티 레포지토리 관리 전략

독립된 저장소들을 운영하면서도 일관성을 유지하기 위한 전략입니다.

### 3.1 공통 자산(Asset) 및 디자인 관리
저장소가 분리되면 UI 컴포넌트를 직접 공유하기 어려우므로 다음 방안을 제안합니다.
- **CSS 프레임워크 표준화**: 모든 프로젝트에서 동일한 **TailwindCSS** 설정이나 **디자인 토큰(JSON)**을 공유하여 시각적 통일성을 유지합니다.
- **공통 자산 호스팅**: 로고, 아이콘, 폰트 등을 별도의 CDN이나 공유 저장소에 두고 모든 프로젝트가 참조하도록 합니다.

### 3.2 API 타입 동기화
- **OpenAPI (Swagger) 활용**: 백엔드에서 생성된 Swagger 문서를 바탕으로 프론트엔드용 클라이언트 코드를 자동 생성하여, 저장소가 다르더라도 API 타입 불일치 문제를 방지합니다.

---

## 4. 장단점 분석 (Trade-offs)

### 장점 (Pros)
- **독립적인 배포 및 개발**: 특정 서비스(`heart`)의 변경사항이 다른 서비스(`store`)에 영향을 주지 않습니다.
- **장애 격리**: 인증 서버만 살아있다면 다른 서비스의 장애가 전체 시스템의 로그인 불능으로 이어지지 않습니다.
- **언어 선택의 자유**: 인증 서버는 Java/Spring으로 유지하고, 신규 서비스는 Next.js(TS)로 만드는 등 상황에 맞는 도구 선택이 가능합니다.

### 단점 (Cons)
- **인프라 복잡도**: 서버 대수가 늘어나고 SSL 인증서 관리 포인트가 많아집니다.
- **데이터베이스 공유 복잡성**: 여러 서비스가 하나의 DB를 바라볼 때 스키마 변경 시 영향 범위가 넓어집니다.

---

## 5. 단계별 이행 제안

1.  **현재 (`aakorea-main`)**: 단일 앱 내에서 인증 로직을 유지하면서 세션 쿠키 도메인만 `.aakorea.org`로 확장 준비.
2.  **분리 단계**: `Auth` 모듈만 따로 떼어내어 `auth.aakorea.org`로 독립 배포.
3.  **신규 개발**: `heart.`, `store.` 등의 신규 리포지토리를 생성하고 `auth.` 서버를 통해 인증을 받도록 설정.

---

## 6. 요약
제안하신 **"별도의 레포지토리 + 독립 인증 서버"** 구조는 유지보수성과 확장성 측면에서 **장기적으로 매우 올바른 방향**입니다. 마이그레이션 도중 제가 각 프로젝트 간의 연결점(CORS, Token Validation, SSO 설정)을 세밀하게 가이드해 드릴 수 있으므로, 구현 난이도에 대해서는 크게 걱정하지 않으셔도 됩니다.
