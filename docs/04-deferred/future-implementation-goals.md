# FUTURE_IMPLEMENTATION_GOALS

## 이 문서의 역할

이 문서는 현재 MVP 범위 밖이지만, 추후 구현 목표로 유지할 기능과 권장 구현 방향을 정리한다.

이 문서가 답하는 질문:

- 어떤 기능을 중장기 구현 목표로 유지할 것인가?
- 현재 구조를 기준으로 각 기능은 어떤 식으로 확장하는 편이 좋은가?
- 어떤 선행 작업과 연관 관계를 고려해야 하는가?

현재 범위 판단의 기준은 `../00-core/PRODUCT_SCOPE.md`,
현재 구현 상태 및 경로의 기준은 `../00-core/ROADMAP.md`를 따른다.

---

## 현재 기준에서의 출발점

현재 구현은 아래 상태를 출발점으로 본다.

- 공개 모임 검색은 **PostGIS 기반의 공간 쿼리(nearby search)**를 제공한다
- `Meeting`에는 주소와 `latitude`, `longitude`가 JTS Point 타입으로 저장되어 공간 계산이 최적화되어 있다
- 범용 첨부파일(`Attachment`) 엔티티와 로컬 스토리지 기반 관리 체계가 구축되어 있다
- 권한 모델(AdminUser, Role, Permission) 및 **감사 로그(Audit Log)** 기록 체계가 구축되어 있다
- 공개 사이트 테마는 draft / publish / rollback 구조를 가진다
- 공개 프론트는 현재 React + Vite SPA이며, 향후 SEO를 위해 SvelteKit 전환을 계획 중이다

## 1. 방문자 경험 강화

### [추가] SEO 및 저사양 모바일 사용자를 위한 SvelteKit 도입
- **이유**: 도움을 필요로 하는 사람들이 네이버/구글 검색을 통해 정보를 빠르게 찾을 수 있도록 노출 순위를 높이고, 저사양 모바일 사용자가 불편함없이 사이트를 이용할 수 있도록 해야 한다.
- **권장 구현 방향**:
    - **SvelteKit 전환**: 공개 사이트(Public) 영역을 SvelteKit으로 전환하여 SSR(Server Side Rendering) 및 정적 페이지 생성을 적용한다. 관리자 영역은 기존 React SPA를 유지한다.
    - **SEO 최적화**: 각 모임 상세 페이지마다 동적 메타 태그 생성 및 Open Graph 정보를 최적화하여 카카오톡/페이스북 공유 시 정보를 한눈에 볼 수 있게 한다.

### [추가] 저사양 모바일 사용자를 위한 디자인 시스템 개선
- **이유**: 저사양 모바일 사용자가 사이트 이용시 심각한 사용 장애를 느끼지 않도록 개선한다.
- **권장 구현 방향**:
    - **CSS 분기 처리**: 클라이언트에 [향상된 속도 vs 유려한 ui] 를 선택할 수 있는 메뉴를 제공하고, 기본값을 '향상된 속도'로 설정한다. 향상된 속도 모드에서는 연산이 많이 필요한 ui 효과를 비활성화하고, GroupDetails 같은 화면에서 지도를 렌더링하지 않는 등의 방법을 고려한다.

### [추가] ContentPage 개선
- **이유**: 컨텐츠를 가장 잘 표현할 수 있는 형태로 ContentPage를 개선한다.
- **권장 구현 방향**:
    - `ContentPage`를 jsx 기반으로 재설계 하고, db 를 효율적으로 관리할 수 있는 방법을 고려한다.

## 2. 관리자 페이지 기능 개선

### [추가] 공개 사이트 메뉴/내비게이션 관리 UI
- **이유**: 코드를 수정하지 않고도 관리자가 직접 헤더/푸터 메뉴를 관리할 수 있어야 한다.
- **권장 구현 방향**:
    - **게시 흐름 재사용**: 현재 공개 테마가 가진 `draft / publish / rollback` 흐름을 메뉴 편집에도 적용한다.
    - **타입 관리**: `HOME`, `MEETINGS`, `NOTICE_LIST`, `CONTENT_PAGE`, `EXTERNAL_URL` 등의 타입을 선택할 수 있게 한다.
    - **드래그 앤 드롭**: 메뉴 순서 변경을 위한 직관적인 UI를 제공한다.

### [보완] ContentPage 자산(매뉴얼/양식) 관리 인터페이스
- **이유**: 안내 페이지 하단에 PDF 매뉴얼이나 신청서 양식을 첨부해야 하는 경우가 많다.
- **권장 구현 방향**:
    - **백엔드**: 이미 구축된 `ContentAttachment` 및 `syncContentAttachments` 로직을 활용한다.
    - **관리자 UI**: `Notice` 관리 화면의 첨부파일 컴포넌트를 `ContentPage` 에도 이식한다.
    - **공개 레이아웃**: 페이지 하단에 첨부파일 목록(파일명, 용량)과 다운로드 링크를 렌더링하는 영역을 추가한다.

### [추가] 대량 데이터 검증 및 리포팅 도구
- **이유**: 전국 270여 개 모임의 데이터 정합성을 효율적으로 유지하기 위함이다.
- **권장 구현 방향**:
    - 주소가 누락되었거나 지오코딩이 실패한 모임, 혹은 장기간 업데이트되지 않은 그룹을 한눈에 보여주는 대시보드를 구축한다.
    - 정기적으로 데이터 상태를 체크하여 관리자에게 알림을 주는 기능을 검토한다.

## 3. 시스템 안정성 및 확장성

### [보완] 로그인 시스템 고도화
- **이유**: 현재 email 기반의 세션 인증을 벗어나 jwt 기반 인증으로 전환하여 다양한 방식의 로그인을 지원하고, 보안성을 높인다. 향후 외부 서비스 연동에 의한 SSO(Single Sign On) 가능성을 염두에 둔다.
- **권장 구현 방향**:
    - 스프링 부트의 Spring Security를 기반으로 jwt 인증을 구현하고, 다양한 로그인 방식을 지원한다. 필요시 OAuth2/OpenID Connect를 통한 외부 서비스 연동을 고려한다.
    - 인증과 인가를 엄격하게 분리한다. 인가 처리는 권한 기반으로 처리한다.

### [보완] 감사 로그(Audit Log) 상세 조회 및 복구 지원
- **이유**: 실수로 정보를 삭제하거나 변경했을 때, 변경 이력을 추적하고 필요시 이전 상태로 복구할 수 있어야 한다.
- **권장 구현 방향**:
    - 현재 구축된 `AuditLog` 모델을 UI에서 더 직관적으로 조회하고, 변경 전/후 값을 JSON Diff 형태로 비교하는 기능을 추가한다.
    - 특정 시점의 데이터로 복구(Restore)하는 기능을 관리자 기능으로 제공한다.

### [추가] 첨부파일 저장 경로 분할 및 자동 정리 (Storage Partitioning & Cleanup)
- **이유**: 파일이 많아질 경우 단일 디렉토리 저장 방식의 성능 저하를 방지하고, 오래된 불필요한 파일을 자동 관리하여 스토리지 효율을 높인다.
- **권장 구현 방향**:
    - **디렉토리 분할**: `uploads/yyyy/MM/`과 같이 연/월 단위로 폴더를 생성하여 파일을 분산 저장한다.
    - **자동 삭제 정책**: 생성 후 5년이 지난 파일은 스케줄러(Spring `@Scheduled`)를 통해 물리 파일과 DB 레코드를 자동으로 삭제한다.
    - **보관 유형 구분**: `Attachment` 엔티티에 `isPermanent`와 같은 필드를 추가하여, 중요 자산은 자동 삭제 대상에서 제외할 수 있도록 기능을 확장한다.
    - **오브젝트 스토리지 전환**: 데이터 규모가 커질 경우 AWS S3 등 오브젝트 스토리지로의 전환을 검토한다. 이 경우 클라우드의 '수명 주기 정책'을 활용해 서버 코드 없이도 자동 삭제 관리가 가능하다.

### [추가] API 문서 자동화 (Swagger/OpenAPI) 도입
- **이유**: 프론트엔드와 백엔드 간의 API 명세 공유를 자동화하여 소통 비용을 줄이고, 향후 모바일 앱 등 다양한 클라이언트 확장에 대비한다.
- **권장 구현 방향**: 
    - **SpringDoc OpenAPI**: `springdoc-openapi` 라이브러리를 도입하여 Spring Boot 프로젝트에 Swagger UI를 통합한다.
    - **보안 설정**: 운영 환경(Production)에서는 Swagger UI 접근을 제한하거나 별도의 인증을 거치도록 설정한다.
    - **문서화 표준**: `Operation`, `Schema`, `ApiResponse` 등의 어노테이션을 적극 활용하여 단순 엔드포인트 나열이 아닌 의미 있는 문서를 구축한다.
