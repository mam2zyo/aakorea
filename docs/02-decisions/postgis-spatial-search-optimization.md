# Decision: PostGIS Adoption for Spatial Search Optimization

## Context
기존의 "내 주변 모임 검색" 기능은 애플리케이션 레벨에서 전체 모임 데이터를 가져와 Haversine 공식을 사용하여 거리를 계산하고 필터링하는 방식(`O(N)` 복잡도)을 사용하고 있었습니다. 모임 데이터가 수천 개 이상으로 늘어날 경우 서버 부하가 증가하고 응답 속도가 저하될 우려가 있었습니다.

## Decision
위객체 기반 검색 성능의 근본적인 향상을 위해 **PostgreSQL의 공간 확장 기능인 PostGIS를 도입**하기로 결정했습니다.

### 주요 결정 사항:
1.  **데이터 저장 방식**: 위도(latitude)와 경도(longitude)를 개별 `Double` 컬럼에 저장하던 방식에서, JTS `Point` 객체를 사용하는 하나의 `geometry(Point, 4326)` 컬럼으로 통합 저장합니다.
2.  **인덱싱**: 공간 쿼리 성능 최적화를 위해 새로운 공간 컬럼에 **GiST(Generalized Search Tree) 인덱스**를 사용합니다.
3.  **검색 로직**: 인메모리 거리 계산을 제거하고, DB 레벨의 위상 함수인 `ST_DWithin`을 활용하여 인덱스를 통한 고속 반경 검색을 수행합니다.

## Rationale
1.  **확장성 (Scalability)**: DB 인덱스를 활용하므로 데이터 양이 늘어나도 검색 성능을 `O(log N)` 수준으로 유지할 수 있습니다.
2.  **정확도**: 지형 모델을 고려한 정확한 공간 연산이 가능합니다.
3.  **코드 복잡도 감소**: 애플리케이션 레벨의 거리 계산 로직을 제거하고 표준화된 공간 함수를 활용하여 서비스 로직을 간결하게 유지할 수 있습니다.
4.  **향후 확장성**: 추후 "특정 지역(Polygon) 내 모임 검색"이나 "경로 기반 검색" 등의 서비스 확장이 용이합니다.

## Consequences
1.  **인프라 요구 사항**: 운영 및 개발 환경(WSL2)에 `postgis` 패키지 설치와 데이터베이스 확장 설정이 필요합니다.
2.  **라이브러리 추가**: Spring Boot 프로젝트에 `hibernate-spatial` 라이브러리 의존성이 추가되었습니다.
3.  **좌표계 관리**: 표준 WGS 84 (SRID: 4326) 좌표계를 엄격히 준수해야 합니다.
4.  **하위 호환성**: 프런트엔드 데이터 규격과의 호환성을 위해 DTO에서는 여전히 위/경도를 개별 필드로 제공합니다.
