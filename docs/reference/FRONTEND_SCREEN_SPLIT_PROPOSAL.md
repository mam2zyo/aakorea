# FRONTEND_SCREEN_SPLIT_PROPOSAL

## 이 문서의 역할

이 문서는 AAKorea Main 웹앱의 현재 MVP 기준으로  
프론트엔드 화면을 **어떤 경계로 분리하는 것이 좋은지** 제안한다.

이 문서가 답하는 질문:

- 공개 화면과 운영 화면을 어떤 기준으로 나누는가?
- 어떤 기능은 별도 화면으로 분리하고, 어떤 기능은 한 화면에 묶어 두는가?
- 최소 라우팅 구조는 어떻게 잡는가?
- 현재 단일 `App` 구조에서 어떤 순서로 화면 분리를 진행하는가?

이 문서에 포함하지 않는 내용:

- 백엔드 API 계약의 상세 정의
- 컴포넌트 단위의 세부 구현 코드
- 화면 디자인 시안의 상세 규칙
- 확정된 일정이나 작업 배정

현재 범위 기준은 `../current/PRODUCT_SCOPE.md`,  
사용자 흐름 기준은 `../current/ACTORS_AND_USE_CASES.md`,  
현재 프론트엔드 상태는 `../current/FRONTEND_STRUCTURE.md`를 따른다.

---

## 제안 배경

현재 프론트엔드는 공개 모임 조회, 운영 인증,  
`District`/`Group`/`GroupContact`/`Meeting` 관리를  
하나의 앱 셸 안에 함께 두고 있다.

이 구조는 초기 MVP 검증 단계에서는 장점이 있었다.

- 공개 흐름과 운영 흐름을 빠르게 한 화면에서 확인할 수 있다
- API 연결 상태를 수직 흐름으로 검증하기 쉽다
- 라우터 없이 빠르게 구현 범위를 확인할 수 있다

하지만 다음 단계에서 `ContentPage`, `Notice`, 공개 안내 화면까지 붙기 시작하면  
한 화면에 너무 많은 맥락이 섞이게 된다.

특히 아래 문제가 커질 가능성이 높다.

- 방문자와 운영자의 사용 맥락이 한 화면에서 충돌한다
- 공개 홈, 공지, 모임 찾기의 역할이 분리되지 않는다
- 운영 기능이 늘어날수록 단일 `App` 파일의 책임이 커진다
- 이후 테스트, 유지보수, 화면별 개선이 어려워진다

따라서 지금 시점에서는 **기능을 많이 늘리기보다, 화면 경계를 먼저 분명히 하는 분리**가 적절하다.

## 화면 분리 원칙

### 1. 첫 번째 기준은 액터다

화면 분리는 먼저 **방문자 영역**과 **운영자 영역**을 나누는 것이 좋다.

- 방문자는 안내, 공지, 모임 탐색이 중심이다
- 운영자는 로그인 후 데이터 관리가 중심이다

즉, 첫 분리 기준은 도메인보다 **사용자 역할 차이**여야 한다.

### 2. 두 번째 기준은 과업 응집도다

같이 수행되는 작업은 가능한 한 같은 화면 안에 남겨 두는 것이 좋다.

예를 들어 `Group`, `GroupContact`, `Meeting`은  
운영자가 하나의 그룹을 관리하는 흐름 안에서 함께 다루는 편이 더 자연스럽다.

반대로 공개 안내와 운영 입력은 같은 화면에 둘 이유가 약하다.

### 3. MVP에서는 화면 수를 과도하게 늘리지 않는다

현재 목표는 복잡한 사이트맵을 만드는 것이 아니라,  
방문자가 길을 잃지 않고 핵심 흐름에 도달하게 하는 것이다.

따라서 화면 분리는 필요하지만,  
세부 엔티티마다 독립 화면을 과하게 늘리는 방식은 현재 MVP에 맞지 않는다.

### 4. 공개 흐름에서는 탐색 순서를 드러내야 한다

방문자에게는 다음 흐름이 자연스럽게 보여야 한다.

1. 서비스가 무엇인지 이해한다
2. 처음 온 사람 안내나 공지를 본다
3. 지역 기준으로 모임을 찾는다
4. 연락처를 확인한다

즉, 공개 화면은 “기능 목록”이 아니라 **이동 순서가 드러나는 구조**가 되어야 한다.

### 5. 운영 화면은 데이터 묶음 기준으로 나눈다

운영 화면은 방문자 화면처럼 스토리 중심이 아니라,  
어떤 데이터를 관리하는지 기준으로 나누는 편이 좋다.

다만 여기서 중요한 점은  
운영 데이터의 편집 단위가 모두 같은 수준은 아니라는 점이다.

- `District`는 독립적인 조직 단위로 관리한다
- `Group`은 실질 관리의 중심 단위로 본다
- `GroupContact`, `Meeting`은 `Group`에 종속된 편집 맥락에서 다룬다

즉, 운영 화면은 엔티티 개수대로 기계적으로 나누기보다  
**실제 편집 책임이 모이는 단위**를 기준으로 분리하는 것이 좋다.

이 판단은 현재 MVP뿐 아니라, 향후 운영 주체가 확장되는 방향과도 맞닿아 있다.

장기적으로는 GSO 관리자만 그룹 정보를 직접 수정하는 구조보다,  
인증된 각 그룹의 GSR가 자기 그룹 정보를 직접 관리하는 흐름을 목표로 둘 수 있다.

이 경우 실제 수정 단위는 여전히 `Group`이 된다.

- 어느 `District`에 속하는지
- 어떤 `GroupContact`를 공개할지
- 어떤 `Meeting` 정보를 노출할지
- 그룹의 긴급한 변경 사항을 어떤 방식으로 공지할지

이런 정보들은 모두 `Group`을 중심으로 함께 관리되는 편이 자연스럽다.

다만 이 GSR 자기관리 흐름은 **현재 MVP 범위에는 포함되지 않으며**,  
현재 문서에서는 향후 확장을 고려한 화면 경계 판단의 근거로만 다룬다.

## 권장 화면 구조

현재 MVP 기준으로는 아래 구조를 권장한다.

### 1. 공개 영역

#### P-01. 홈 화면

- 경로: `/`
- 역할: 서비스 소개, 첫 방문자 안내 진입, 최신 공지 요약, 모임 찾기 진입

이 화면은 방문자가 처음 들어왔을 때  
서비스의 목적을 이해하고 다음 행동을 고를 수 있게 해야 한다.

현재 MVP에서는 아래 요소만 있으면 충분하다.

- 서비스 소개 요약
- “처음 오신 분 안내” 대표 링크
- 최신 공지 3~5건 요약
- “모임 찾기” 바로가기

즉, 홈 화면은 정보를 모두 담는 곳이 아니라  
핵심 공개 흐름으로 보내는 **관문 화면**이어야 한다.

#### P-02. 안내/정적 페이지 화면

- 경로: `/pages/:key`
- 역할: `ContentPage` 기반 안내성 콘텐츠 노출

예:

- `/pages/first-visitor-guide`
- `/pages/about-aa`

`ContentPage`는 비교적 안정적인 설명성 콘텐츠이므로,  
개별 페이지 단위로 보여 주는 것이 자연스럽다.

#### P-03. 공지 목록 화면

- 경로: `/notices`
- 역할: 공개된 `Notice` 목록 조회

홈 화면에서는 공지를 요약만 보여 주고,  
전체 목록 탐색은 별도 화면으로 분리하는 편이 좋다.

#### P-04. 공지 상세 화면

- 경로: `/notices/:id`
- 역할: 공지 본문 확인

`Notice`는 목록과 상세의 역할이 분명하므로  
목록/상세 2화면 구조가 적절하다.

#### P-05. 모임 찾기 화면

- 경로: `/meetings`
- 역할: 지역 기준 검색, 결과 목록, 상세 확인, 연락처 확인

이 화면은 현재 MVP의 핵심 흐름이므로 별도 독립 화면이어야 한다.

다만 여기서 중요한 점은  
**목록과 상세를 지금 당장 완전히 다른 상위 화면으로 쪼개지 않는 것**이다.

초기 MVP에서는 아래 구조가 적절하다.

- 데스크톱: 목록 + 상세의 분할 화면
- 모바일: 목록 우선, 선택 시 상세 강조

즉, “모임 찾기”는 하나의 과업이므로  
상위 경로는 하나로 유지하고 내부 표현만 화면 크기에 맞게 조정하는 편이 좋다.

---

### 2. 운영 영역

#### A-01. 운영 로그인 화면

- 경로: `/admin/login`
- 역할: 운영자 인증 진입

현재처럼 공개 화면 안에 로그인 패널을 함께 두기보다,  
운영 진입은 별도 경로로 분리하는 것이 좋다.

이렇게 하면 방문자 화면과 운영 화면의 심리적 경계도 분명해진다.

#### A-02. 운영 District 관리 화면

- 경로: `/admin/districts`
- 역할: `District` 목록/생성/수정

`District`는 현재 MVP에서는 비교적 단순해 보일 수 있다.

하지만 이후 조직 구조가 더 복잡해질 가능성이 높고,  
운영 기준 단위로서 독립적인 의미가 있으므로  
초기부터 별도 화면으로 분리해 두는 편이 좋다.

즉, 지금 화면이 다소 비어 보이더라도  
`District`는 `Group` 편집 화면 안에 흡수하지 않는 편이 바람직하다.

#### A-03. 운영 Group 목록 화면

- 경로: `/admin/groups`
- 역할: `Group` 목록 조회, 생성 진입, 편집 진입

실제로 운영 관리의 핵심 주체는 `Group`이다.

운영자는 보통 아래 흐름으로 작업하게 된다.

- 어떤 District 아래에 Group이 있는지 본다
- 관리할 Group을 선택한다
- 해당 Group의 연락처와 모임까지 함께 점검한다

따라서 운영 메인 진입점은 `Meeting` 단독 화면보다  
`Group` 목록 화면이 되는 편이 더 자연스럽다.

새 `Group` 생성도 여기서 시작하는 것이 좋다.

초기 생성에서는 최소한의 `Group` 정보만 저장하고,  
저장 직후 해당 `Group` 편집 화면으로 이동해  
`GroupContact`와 `Meeting`을 이어서 입력하게 하는 흐름이 자연스럽다.

#### A-04. 운영 Group 편집 화면

- 경로: `/admin/groups/:id`
- 역할: `Group` 기본 정보, `GroupContact`, `Meeting`을 한 작업 맥락에서 편집

이 화면은 운영 화면에서 가장 중요한 작업 공간이다.

`Meeting`은 `Group` 없이 단독으로 존재할 수 있는 객체가 아니므로,  
운영자도 `Meeting`을 독립된 최상위 관리 대상처럼 다루기보다  
**특정 Group에 속한 정보**로 수정하는 편이 자연스럽다.

이 화면에서는 아래가 함께 가능해야 한다.

- Group 기본 정보 수정
- GroupContact 목록/생성/수정
- Meeting 목록/생성/수정
- 현재 Group에 연결된 참조 상태 확인

즉, `Group` 편집 화면은 단순 폼이 아니라  
해당 Group의 공개 운영 정보를 한 번에 관리하는 **작업 공간형 화면**이 되어야 한다.

또한 이 화면은 향후 GSR 자기관리 흐름으로 확장될 때도  
가장 자연스럽게 재사용될 수 있는 화면이어야 한다.

장기적으로는 인증된 그룹 GSR가 이 화면을 통해 자신의 그룹 정보를 직접 수정하는 구조를 상정할 수 있다.

그 경우 이 화면에서 다뤄야 할 책임은 다음처럼 확장될 수 있다.

- Group 기본 정보 수정
- 소속 `District` 변경 또는 확인
- 공개 연락처 수정
- 모임 정보 수정
- 그룹의 긴급 변경 사항에 대한 공지 또는 안내 입력

즉, `Group` 편집 화면은 현재 MVP에서는 GSO 운영 화면이지만,  
장기적으로는 **그룹 단위 셀프서비스 편집 화면**의 기반이 될 가능성이 높다.

다만 이 권한 확장과 인증 모델은 현재 MVP 범위 밖이며,  
현재 단계에서는 화면 구조를 미래 확장에 무리 없이 맞추는 수준까지만 고려한다.

#### A-05. 운영 정적 페이지 관리 화면

- 경로: `/admin/content-pages`
- 역할: `ContentPage` 목록/생성/수정

정적 안내성 콘텐츠는 `Group` 중심 운영 화면과 성격이 다르므로  
별도 화면으로 분리하는 것이 자연스럽다.

#### A-06. 운영 공지 관리 화면

- 경로: `/admin/notices`
- 역할: `Notice` 목록/생성/수정

`Notice`는 시간 민감성과 목록성이 강하므로  
`ContentPage`와 구분된 관리 화면으로 두는 것이 좋다.

## 분리하지 않는 것이 좋은 부분

현재 MVP 단계에서는 아래 분리는 보류하는 편이 좋다.

### 1. GroupContact 와 Meeting 의 최상위 분리

`GroupContact`와 `Meeting`은 `Group`에 종속된 데이터다.

지금 단계에서 이를 `/admin/group-contacts`, `/admin/meetings`처럼  
최상위 운영 화면으로 완전히 분리하면, 실제 편집 단위와 화면 구조가 어긋날 수 있다.

따라서 초기에는 `Group` 편집 화면 안에서 함께 다루는 편이 낫다.

### 2. District 를 Group 화면에 흡수

`District`는 현재 단순해 보여도 이후 확장 가능성이 있는 조직 단위다.

그래서 `District`를 `Group` 관리 화면 안의 부속 섹션으로 두기보다,  
초기부터 별도 화면으로 유지하는 편이 구조적으로 더 안정적이다.

### 3. 운영 대시보드 신설

현재 MVP에서는 별도 대시보드가 꼭 필요하지 않다.

`/admin`은 단순 리다이렉트로 `/admin/groups`로 보내도 충분하다.

대시보드는 운영 데이터가 더 많아졌을 때 다시 검토하는 편이 낫다.

### 4. GSR 전용 별도 편집 화면 선분리

향후 GSR 자기관리 기능이 추가되더라도,  
초기부터 GSO용 화면과 GSR용 화면을 완전히 다른 구조로 분리해 둘 필요는 없다.

우선은 `Group` 중심 편집 화면을 잘 정의해 두고,  
이후 권한에 따라 노출 범위와 편집 가능 범위를 조정하는 쪽이 더 자연스럽다.

즉, 지금은 별도 GSR UI를 만드는 것보다  
**Group 편집 화면 자체를 미래 확장 가능한 작업 공간으로 설계하는 것**이 우선이다.

### 5. 공개 모임 목록/상세의 상위 경로 분리

초기 MVP에서는 “모임 찾기”가 하나의 과업이다.

따라서 `/meetings`와 `/meetings/:id`를 완전히 다른 상위 화면 경험으로 만들기보다,  
우선은 같은 탐색 흐름 안에서 처리하는 편이 자연스럽다.

필요하다면 이후에 URL 상태를 추가할 수 있지만,  
지금은 화면 분리보다 탐색 연속성이 더 중요하다.

---

## 권장 라우팅 구조

아래 정도의 최소 구조를 권장한다.

### 공개 라우트

- `/`
- `/pages/:key`
- `/notices`
- `/notices/:id`
- `/meetings`

### 운영 라우트

- `/admin/login`
- `/admin/districts`
- `/admin/groups`
- `/admin/groups/:id`
- `/admin/content-pages`
- `/admin/notices`

### 공통 동작

- `/admin/*`는 인증 필요
- 미인증 상태에서 `/admin/*` 접근 시 `/admin/login`으로 이동
- 로그인 완료 후 원래 접근하려던 운영 경로로 복귀 가능하면 더 좋다

---

## 권장 레이아웃 구조

화면 분리와 함께 레이아웃도 두 축으로 나누는 것이 좋다.

### 1. `PublicLayout`

역할:

- 공개 상단 내비게이션
- 서비스 소개 톤 유지
- 공지/안내/모임 찾기 이동 제공

권장 메뉴:

- 소개
- 처음 오신 분 안내
- 공지
- 모임 찾기
- 운영자 로그인

### 2. `AdminLayout`

역할:

- 운영자 전용 내비게이션
- 현재 로그인 상태 표시
- 로그아웃
- 데이터 관리 메뉴 제공

권장 메뉴:

- District 관리
- Group 관리
- 페이지 관리
- 공지 관리

즉, 화면 분리는 단지 페이지를 나누는 것이 아니라  
**공개용 셸과 운영용 셸을 분리하는 것**까지 포함해야 효과가 크다.

---

## 권장 프론트엔드 파일 구조

현재 MVP에서 과하지 않은 수준으로는 아래 구조를 제안한다.

```text
src/
  App.jsx
  app/
    router.jsx
  layouts/
    PublicLayout.jsx
    AdminLayout.jsx
  pages/
    public/
      HomePage.jsx
      ContentPageView.jsx
      NoticeListPage.jsx
      NoticeDetailPage.jsx
      MeetingSearchPage.jsx
    admin/
      AdminLoginPage.jsx
      DistrictAdminPage.jsx
      GroupListPage.jsx
      GroupEditorPage.jsx
      ContentPageAdminPage.jsx
      NoticeAdminPage.jsx
  components/
    common/
    public/
    admin/
  lib/
    api.js
    options.js
```

핵심은 파일 수를 많이 만드는 것이 아니라,  
`App.jsx`가 모든 화면 책임을 직접 갖지 않게 만드는 것이다.

---

## 단계별 전환 제안

현재 구조에서 한 번에 크게 갈아엎기보다 아래 순서를 권장한다.

### 1단계. 현재 `App.jsx`를 공개/운영 블록으로 먼저 분리

먼저 라우터를 도입하기 전이라도 아래 단위로 컴포넌트를 분리한다.

- 공개 모임 조회 블록
- 운영 로그인 블록
- District 관리 블록
- Group 목록 블록
- Group 작업 공간 블록

이 단계의 목표는 **기능 변경 없이 책임만 분리**하는 것이다.

### 2단계. `PublicLayout`, `AdminLayout`, 최소 라우터 도입

그다음 공개/운영 셸을 분리하고 경로를 붙인다.

이 단계에서는 우선 아래만 분리해도 충분하다.

- `/meetings`
- `/admin/login`
- `/admin/districts`
- `/admin/groups`
- `/admin/groups/:id`

### 3단계. 콘텐츠 API 구현과 함께 공개 홈/공지/정적 페이지 추가

`ContentPage`, `Notice`가 구현되면 아래 공개 화면을 붙인다.

- `/`
- `/pages/:key`
- `/notices`
- `/notices/:id`

즉, 화면 분리와 콘텐츠 구현은 같이 가는 편이 가장 자연스럽다.

### 4단계. 운영 콘텐츠 관리 화면 추가

콘텐츠 관리 API가 준비되면 운영 쪽에 아래를 추가한다.

- `/admin/content-pages`
- `/admin/notices`

### 5단계. 모바일 표현과 URL 세부 정책 정리

마지막으로 모바일에서 모임 상세를 어떻게 보여 줄지,  
필요하다면 선택 상태를 URL에 반영할지 검토한다.

이 부분은 핵심 분리 이후에 다뤄도 충분하다.

---

## 기대 효과

이 제안대로 분리하면 다음 효과를 기대할 수 있다.

- 방문자 입장에서 “어디서 무엇을 해야 하는지”가 더 분명해진다
- 운영자 입장에서 관리 대상별 작업 맥락이 정리된다
- `App.jsx`의 책임이 줄어들어 유지보수가 쉬워진다
- 콘텐츠 MVP가 추가돼도 공개 흐름이 어수선해지지 않는다
- 이후 테스트를 화면 단위로 나누기 쉬워진다

---

## 최종 제안 요약

현재 MVP에서 가장 적절한 방향은 다음과 같다.

1. 먼저 **방문자 영역**과 **운영자 영역**을 분리한다
2. 공개 영역은 `홈 / 안내 페이지 / 공지 / 모임 찾기`로 나눈다
3. 운영 영역은 `로그인 / District 관리 / Group 관리 / 페이지 관리 / 공지 관리`로 나눈다
4. `Group` 편집 화면 안에서 `GroupContact`와 `Meeting`을 함께 관리한다
5. `District`는 지금 다소 단순해 보여도 독립 화면으로 유지한다
6. 이 구조는 향후 인증된 GSR의 그룹 셀프서비스 편집 흐름으로도 확장 가능하다
7. `모임 찾기`는 아직 하나의 과업 화면으로 유지한다

즉, 지금 필요한 것은 “많은 화면”이 아니라  
**사용자 역할과 과업 흐름이 드러나는 최소한의 화면 분리**다.
